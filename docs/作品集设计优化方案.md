# 个人作品集 · 设计优化方案

> 状态：**方案稿（本轮不动代码）** · 起草 2026-10-21
> 对象：`portfolio/index.html`（185 行，Tailwind vendor 运行时 410 KB + iconify 22 KB）、`css/site.css`（15 行）、`js/site.js`（51 行）
> 判定基准：文件是事实，**未在浏览器里实际截图**；涉及视觉效果的结论标注「需实测」。

---

## 0. 先说三个硬伤（不改代码也要知道）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | **作品卡信息密度过高** | 乒乓卡正文约 480 字、返航录卡约 760 字，全是粗体强调与括号补充 | 招聘方/客户在首屏扫视时会直接略过；移动端卡片高度爆炸 |
| 2 | **数据与内容不同步** | 首页写「4 个项目 / 3 年经验 / 4.8 评分」，而 `projects.json` 已含 4 个条目、实际还有一个未展示的「游戏包」 | 数据自证性弱；新增项目后容易忘记更新 |
| 3 | **首屏只有一句话 + 一个按钮** | `min-h-[calc(100vh-80px)]` 的 Hero 区仅文字 | 没有作品画面做「第一印象」，与「作品集」的用途不匹配 |

另外两处工程隐患：
- `js/vendor/tailwindcss.js` 是**浏览器端运行时**，410 KB，且与手写 `site.css` 里的 `!important` 规则混用（`site.css` 有 5 处 `!important` 覆盖 Tailwind 类）——迭代久了会互相打架。
- 首页所有作品卡是**手写重复 HTML**（每张卡结构相同、文案不同），`projects.json` 只服务于预览弹窗，**没有驱动渲染**——加一个项目要改两处。

---

## 1. 设计目标（改版后应达到）

1. **3 秒能看懂**：你是谁、做什么、最好的三件作品分别是什么。
2. **作品先于文字**：每张卡首屏只有「一句话 + 一个视觉」，细节放进详情页/弹窗。
3. **移动优先**：390×844 下首屏不滚动就能看到至少一张作品卡的头图。
4. **数据单一来源**：卡片数量、标签、链接全部从 `projects.json` 渲染，改一处生效。
5. **可维护**：不再有 `!important` 打架；样式改动集中在一个 token 文件。

---

## 2. 视觉方向（三选一，建议 B）

| 方案 | 关键词 | 成本 | 适配你的作品 |
|---|---|---|---|
| A. 现状强化 | 深色 + 靛紫渐变 + 粒子背景 | 低 | 安全但同质化严重（大量 AI 作品集都是这套） |
| **B. 深色 + 单强调色 + 作品当主角**（推荐） | 近乎纯黑底（#0B0B0F）+ **一个**暖色强调（如琥珀 #F5A524 或青 #2DD4BF）+ 大图 + 极简文字 | 中 | 和两个游戏的 UI 语言（乒乓琥珀金强调、返航录深蓝）能对上，视觉上「像一个人的作品」 |
| C. 杂志排版 | 大量留白 + 衬线标题 + 全宽图 | 中高 | 最像「设计作品集」，但你的项目偏工程，容易显得刻意 |

**建议 B 的具体做法**：
- **只有一处强调色**（当前 `#6366f1` 用在按钮、链接、hover、边框、二维码按钮——6 处以上，等于没有强调色）。
- **渐变只保留在 Contact 区**（现在是 Hero 标题 + 按钮 + Contact 三处都用渐变）。
- **粒子背景降级为可选**：`prefers-reduced-motion` 时关闭；移动端降为 24 个点或直接去掉（当前 42 点 + O(n²) 连线，在低端机上是纯耗电）。

## 3. 信息架构调整

```
现状：[Hero 一大段] → [4 个数字条] → [作品 ×4] → [Contact]

建议：
① Hero（左文案 / 右 = 最新项目的动态截图或短视频静帧，自动轮播 2 张）
② 精选 3 件（不是 4 件）：大卡 ×1 + 中卡 ×2，卡片只放：类别 / 标题 / 一句价值句 / 3 个标签
③ 「全部项目」抽屉：项目数由 projects.json 决定，可以随时加
④ 能力带：把「3 年经验 / 4 个项目 / 4.8 评分」换成有证据的写法（见 §6）
⑤ Contact（保持）
```

**卡片信息分级**（关键改动）：

| 层级 | 内容 | 位置 |
|---|---|---|
| L1 卡片 | 类别徽章、标题、**一句价值句（≤28 字）**、3 个标签、一个主链接 | 列表页 |
| L2 弹窗 | 关键数据（如「10000 局模拟」「ITTF 标准」）、技术要点 3 条、截图 | 点开 |
| L3 详情页 | 长文、变更记录、下载、二维码 | 新窗口独立页 |

> 现在 760 字的返航录描述，应拆到 L2/L3；L1 只写「15 人三阵营身份博弈，AI 托管空席，手机横屏可玩」。

## 4. 工程改造（与设计同步做）

| 项 | 现状 | 建议 | 收益 |
|---|---|---|---|
| 样式 | Tailwind 浏览器运行时 + 15 行手写 CSS + 5 处 `!important` | **改用 Tailwind CLI 预编译**（产出 ~15 KB CSS，只保留用到的类），`site.css` 变成 `tokens.css`（颜色/间距/圆角变量）+ 少量组件类 | 首屏少下载 ~395 KB；不再需要 `!important` |
| 渲染 | 卡片手写 HTML | `projects.json` → 模板函数渲染（约 60 行 JS，无框架） | 加项目只改 JSON |
| 图片 | PNG 直出（`assets/projects/*.png`） | 出 WebP/AVIF，`<picture>` + `loading="lazy"` + 明确 `width/height` | 首屏 CLS=0；体积通常 −60% |
| 图标 | iconify 运行时按名加载 | 把用到的 8–10 个图标**内联为 SVG** | 少一个 22 KB 依赖 + 少一次网络往返 |
| 动效 | 粒子循环 | 保留但加 `prefers-reduced-motion`，移动端降频 | 省电、无障碍 |
| 可访问性 | 卡片是 `onclick` 的 `<article>` | 改为 `<a>` 或加 `role="button" tabindex="0"` + 键盘事件 | 键盘可达、屏幕阅读器可读 |
| 预览弹窗 | iframe `sandbox` 已配 | 保持；补 `title` 与 `aria-modal="true"` | 无障碍 |

## 5. 文案改写原则

1. **一句一事实**，括号补充最多一个。
2. **不用「零依赖」「纯 JavaScript」这类自我表扬**作为卖点，改成结果：「离线可用」「首次加载 < 200 KB」。
3. 数字要有出处与日期：「10000 局蒙特卡洛（2026-09）」优于「大规模模拟」。
4. 每张卡最多一个 **bold**。

示例（返航录 L1）：
> **返航录 · 三阵营对抗**
> 15 人身份博弈，AI 托管空席，手机横屏可玩。
> `网页游戏` `博弈 AI` `蒙特卡洛`

---

## 6. 「数字条」怎么改

现在的「3 年 / 4 个项目 / 4.8 评分 / 4 个行业」有两个问题：4.8 评分无出处；项目数与实际不同步。建议改成**可验证的三项**：

- `2` 个可玩网页游戏（含联机）
- `10,000` 局蒙特卡洛验证（返航录平衡性）
- `4` 个已上线项目（口径：各自主域名可访问）

> 如果「4.8/5 合作满意评分」有真实来源（客户评价截图/邮件），保留并加脚注；没有就删掉——作品集里最伤信任的是无法验证的好话。

## 7. 分阶段实施

| 阶段 | 内容 | 风险 | 回滚 |
|---|---|---|---|
| D0 | 备份 + 截一份当前首页（作为对比基线） | 无 | — |
| D1 | 抽 `tokens.css`（颜色/字号/间距变量），不改视觉 | 低 | git |
| D2 | 卡片数据化：`projects.json` 驱动渲染 | 中（要保证弹窗逻辑不变） | git |
| D3 | 视觉改版：单强调色 + Hero 右侧作品图 + 卡片信息分级 | 中 | git（保留旧 `index.html` 一份副本） |
| D4 | Tailwind 预编译替换运行时 | 中（需要本地构建步骤，与「无构建」路线冲突 → 见风险） | 保留 vendor 文件即可退回 |
| D5 | 图片 WebP + 图标内联 + 无障碍修补 | 低 | git |
| D6 | 与游戏包卡片合流（新增大厅项目） | 由游戏包方案决定 | git |

**关于 D4 的风险**：你的部署是「白名单静态发布」，没有构建步骤。引入 Tailwind CLI 意味着 `deploy` 前必须多跑一步 `npm run css`，否则会上线旧样式。两种取舍：
- 引入构建（CSS 更小、更干净，但多一步、需要 CI 里加命令）；
- 维持运行时（零构建，但 410 KB）。
**建议：先做 D1–D3、D5，D4 单独决策**——它的收益主要在网络较差的手机上。

---

## 8. 验收（每个阶段都要）

- 六档视口（320/360/390/430/768/1280）无横向滚动、无文字裁切（沿用乒乓口径）。
- Lighthouse 移动端：性能 ≥ 85、可访问性 ≥ 95（D4 后应 ≥ 92 性能）。
- 首屏到可交互 < 2.5s（4G 模拟，DevTools）。
- `prefers-reduced-motion` 下无动画、无「空白图」。
- 键盘 Tab 能走完所有卡片与按钮，Esc 能关弹窗。
- 首页文案与 `projects.json` 项目数一致（加一个 `node tools/check-copy.cjs` 校验）。
